# Real payment gateways: Razorpay, PhonePe, Paytm

These adapters call the providers' **real HTTP APIs** in **test/sandbox mode**. Customers really are redirected to the provider's checkout; the provider really signs its callbacks; the platform really verifies them and posts the ledger. Only the money is fake (test mode). Live keys and production hosts are refused in code, matching the platform-wide `PAYMENT_MODE=live` block.

Select with `PROVIDER_KIND=razorpay|phonepe|paytm` in `backend/.env` and fill that provider's variables (`.env.example`). The webhook URL to register at the provider is `PUBLIC_BASE_URL/webhooks/<razorpay|phonepe|paytm>` (must be publicly reachable, e.g. via a tunnel in development).

## What each adapter does

| | Razorpay | PhonePe | Paytm |
|---|---|---|---|
| Create payment | Orders API; our merchant id goes in `notes` | `/pg/v1/pay` (X-VERIFY, salt key); redirect to PhonePe's page | `initiateTransaction` (checksum) then our `/pay/paytm/:order` page posts to Paytm's payment page |
| Customer checkout | our `/pay/razorpay/:order` page loads Razorpay `checkout.js` | PhonePe-hosted | Paytm-hosted |
| Confirm | `GET /v1/payments/:id` (+ order notes for the merchant) | `GET /pg/v1/status/:mid/:txn` | `POST /v3/order/status` |
| Webhook auth | `X-Razorpay-Signature` HMAC-SHA256 | `X-VERIFY` = sha256(response+salt)###index | `CHECKSUMHASH` over the form params |
| Refunds | yes (idempotent via refund notes) | **no** (status API reports no refunded amount, so reconciliation could not verify) | yes (`refId` derived from our idempotency key) |
| Transaction listing / reconciliation sweep | yes | **no** (501 `CAPABILITY_UNAVAILABLE`) | **no** (501) |
| Merchant payouts | no | no | no |

Unsupported things throw (`PAYOUTS_UNSUPPORTED`, `REFUNDS_UNSUPPORTED`, `CAPABILITY_UNAVAILABLE`); they are never faked. Merchant payouts are a different product at each provider (e.g. RazorpayX) and need their own contract.

## Safety properties (all tested)
- The webhook body is never trusted for amount or status: it only names a payment; the amount and status come from the provider's status API.
- Forged, tampered or unsigned webhooks are rejected and counted; redelivered ones are deduplicated.
- A captured payment with the wrong amount goes to manual review, not to the merchant.
- Razorpay `authorized` (not captured) is treated as pending, never as money received. Turn on auto-capture in the Razorpay dashboard.
- Paytm and PhonePe do not echo a merchant reference on status lookups, so attribution comes from our own `payment_requests` row for that order id (it is our order id, generated by us).

## What is verified and what is not
Automated tests (`backend/test/gateways.spec.ts`, 24 tests) run each adapter over real HTTP against **mock provider servers** that check authentication and signatures the way each provider's documentation describes, plus the full flow through the platform (webhook, verification, ledger, review).

**Not verified:** any call against the real Razorpay, PhonePe or Paytm servers. That needs your test credentials. Field names and signature schemes were written from the providers' public docs and may drift: PhonePe in particular has been moving from the salt-key API used here to a newer OAuth-based API, and its sandbox may require the newer one. Run one real test-mode payment per provider before relying on an adapter, and record real webhook samples as fixtures (step 3 of [provider-integration-checklist.md](provider-integration-checklist.md)).

## Trying it
1. Create a free test account at the provider and copy its test credentials into `backend/.env`.
2. `PROVIDER_KIND=razorpay npm start` (or `phonepe`, `paytm`).
3. Follow "Try the sandbox flow" in the README; the checkout URL now opens the provider's real test checkout.
4. Expose `PUBLIC_BASE_URL` publicly and register the webhook URL at the provider so payment confirmations arrive.
