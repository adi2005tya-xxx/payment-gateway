# Disaster recovery runbook

Scope: PostgreSQL (the only system of record) for the Gateway backend. Verified results: [dr-test-report.md](dr-test-report.md) (generated by `backend/scripts/dr-drill.ts`). Anything not exercised by that drill is marked **untested**.

## 1. What is protected and how
| Layer | Mechanism | Exercised in the drill |
|---|---|---|
| Base backup | Physical backup (`pg_backup_start` / copy data dir / `pg_backup_stop`) packaged by `src/recovery/backup-archive.ts`: AES-256-GCM, per-file SHA-256 manifest, sidecar with SHA-256 of the encrypted file | Yes |
| Continuous archive | `archive_mode=on`, `archive_command` = `src/recovery/wal-archive.js` (each segment AES-256-GCM encrypted, segment name as AAD, atomic publish, refuses to overwrite a different segment) | Yes |
| Point-in-time recovery | `restore_command` + `recovery_target_time` / latest, `recovery_target_action=promote` | Yes |
| Managed-service equivalents (RDS/Cloud SQL/Azure snapshots, PITR) | Same physical mechanics, provider-run | **Untested** (no managed service available here) |
| Logical dumps (`pg_dump`) | Not used. The embedded test binaries do not include `pg_dump`. | **Untested** |

Production should use the managed PostgreSQL's native snapshots + PITR **and** this repo's integrity/post-restore procedure; the drill script is the executable specification of what a restore must prove.

## 2. Objectives (proposed, to be approved by the business)
- **RPO: 5 minutes** with WAL archiving (`archive_timeout = 60`). The drill measured actual loss of a batch that was committed but not yet archived when the primary was destroyed, so RPO = time since the last *archived* segment. Near-zero RPO needs synchronous replication to a second site (**not configured**).
- **RTO: 2 hours** for a database of the size operated at launch, covering detection, provisioning, restore, verification and the manual post-restore reconciliation. The drill's measured *technical* restore time (decrypt, replay, verify) for its small synthetic database is in the report; it excludes provisioning, DNS cut-over and reconciliation, and must be re-measured on production-sized data.
- Re-measure after any change in data volume (>2x), PostgreSQL major version, or backup tooling.

## 3. Backup security
- **Encryption:** backups and WAL are encrypted before leaving the primary host (above). The drill scans every backup and archive file for known plaintext (names, emails, table names, `PG_VERSION`) and for the keys themselves.
- **Keys:** two independent 32-byte keys (backup container, WAL archive). They must **not** live in the backup bucket, the database, the application repo or logs. Recommended custody: (a) secrets manager/KMS in the primary account for day-to-day use; (b) an offline escrow copy (sealed, split between two named custodians, stored in a different location) so that a total loss of the cloud account does not make every backup unreadable. Escrow retrieval and a test restore using only the escrow copy must be rehearsed (**not done**: the drill uses key files in a separate directory).
- **Rotation:** the container format has no key-id agility beyond `keyId` in the sidecar; rotate by taking a new base backup under the new key and keeping old keys until their backups expire. Per-backup data keys wrapped by a KMS key (so individual backups can be crypto-shredded) are **recommended, not implemented**.
- **Access:** (recommended, not enforced by this repo) archive writer = append-only role without delete; restore role separate and MFA-protected; no human has standing read access to backups; access logged.
- **Failure domains:** the drill keeps backups and the archive on the same disk as the test cluster, so it proves mechanics only. Production must store them in a different account/region and, to resist ransomware or a compromised cloud account, use object-lock/WORM with a separate account for deletion rights. **Regional-failure and ransomware resistance are NOT claimed**; they depend on infrastructure not present in this repository.
- **Logs/artifacts:** the restore tooling logs paths and counts only; the `wal-archive.js` helper prints no data. The key never appears in the sidecar manifest (tested).
- **Retention (proposal, confirm with counsel for financial-record duties):** base backups daily, kept 35 days, monthly kept 12 months; WAL kept from the oldest retained base backup. Deletion by lifecycle rule; with a single key for all backups, deletion is only logical until per-backup keys exist.

## 4. Before relying on a backup (every backup)
1. `verifyBackupChecksum(file)`: size and SHA-256 match the sidecar (works without the key).
2. WAL continuity check from the backup's start segment to the newest archived segment (`walGaps` in the drill). **Run this before recovery: with no recovery target, PostgreSQL silently promotes at the first missing segment.**
3. Scheduled (monthly) full restore drill: `cd backend && npm run dr:drill`.

## 5. Restore procedure
Never restore over a live data directory (the tooling refuses a non-empty target). Always restore into a **new** server/volume and cut over only after verification.

1. **Declare** the incident; stop the application and workers (or leave them stopped). Decide the target: *latest* or a specific time (`recovery_target_time`, before a corruption event).
2. **Provision** a fresh PostgreSQL of the same major version (or higher only if tested).
3. **Verify and extract** the chosen base backup: `restoreEncryptedBackup(file, key, newDataDir)` checks the checksum, GCM tag, every file hash and the manifest before writing anything (staged, then renamed).
4. **Configure recovery**: add `restore_command` (see `restoreCommand()` in `src/recovery/pgcluster.ts`), `recovery_target_time` if needed, `recovery_target_action = 'promote'`, create `recovery.signal`, start the server, wait until `pg_is_in_recovery()` is false.
5. **Apply migrations only if the restored `schema_migrations` is behind** the application release you will start: run the normal `migrate` once. Never replay old migrations. The integrity check fails if the database contains a migration the application does not know (backup newer than the code).
6. **Run the integrity checks** (`verifyFinancialIntegrity`, 18+ invariants incl. journals balance, trial balance, accounting equation, merchant balances re-derived from payments/refunds/payouts, payout reservation/completion/release consistency, refund compensation, unique keys, audit chain, schema equals a freshly migrated one) and, if you kept a pre-incident snapshot, `diffSnapshots`.
7. **Start the application with the restored database.** On start it compares the database incarnation (`system_identifier:timeline`) to the one stored in `system_flags`; any restore, PITR or failover changes it and **automatically freezes money-out** (no new payouts or refunds; queued payouts are deferred, never submitted). Inbound webhook/payment processing continues.
8. **Run the post-restore procedure** (`RecoveryService.postRestore`; also freezes if step 7 did not detect the restore, e.g. a restored logical copy in the same cluster):
   - revokes **all** login sessions (a revocation made after the backup would otherwise be undone);
   - applies payments the provider captured after the backup point (idempotent, inbound only);
   - for each payout in flight (SUBMITTED/PROCESSING) looks it up at the provider **by our reference** (read-only): found → adopt the provider's state; not found or provider unreachable → **hold for review** (`RESTORE_UNKNOWN_OUTCOME`), funds stay reserved;
   - payouts still QUEUED are adopted if the provider already holds them, otherwise left QUEUED and **not submitted**;
   - runs reconciliation and reports.
9. **Resolve what is left**, from provider evidence only:
   - held payouts: `POST /admin/recovery/payouts/:id/resolve` — `sync` (provider has it) or `confirmed_not_sent` (provider has no record **and** an admin attests, with a written note, that statements show no transfer). Needs MFA step-up.
   - `ORPHAN_PROVIDER_PAYOUT` (provider paid something the restored DB has no record of — happens when the backup is older than the payout): there is deliberately no automatic adoption. Record it through a reviewed, audited compensating journal and payout record, or the merchant's balance is overstated and a second payment could follow. **Release stays blocked until reconciliation is clean.** Use the adoption procedure: `POST /admin/recovery/adoptions` (administrator A, with the reason it was matched) then `POST /admin/recovery/adoptions/:id/decision` (a different administrator). The amount and status come from the provider's own record; the same journals as a normal payout are posted; reconciliation then matches it by provider id.
   - pending refunds complete themselves by replaying `createRefund` with the refund's idempotency key (a required provider capability) even while frozen.
10. **Release**: `POST /admin/recovery/unfreeze` (MFA step-up). It refuses unless no payouts are in flight/held and a **fresh** reconciliation has zero open discrepancies.
11. After release: have admins regenerate recovery codes (codes used after the backup point are "unused" again in the restored data) and review `MFA_*` alerts; expect re-sent notifications (`notification_jobs` are replayed).

### Re-running a restore
Safe. Restoring the same backup twice gives identical financial content (tested by hash, not row counts); re-running the post-restore procedure changes no posted record and never calls the provider to create anything (tested).

## 6. Failure playbooks (what the tests cover)
| Situation | Behaviour | Tested |
|---|---|---|
| App crash mid-webhook (after ledger write, before commit) | Transaction rolled back; event stays RECEIVED; replay applies exactly once | Real PostgreSQL + PGlite |
| Database killed mid-transaction | Uncommitted rows absent after crash recovery; snapshot unchanged | Real PostgreSQL |
| Worker restart with queued events | Queue preserved by backup; jobs run once; while frozen no external money moves | Real PostgreSQL + PGlite |
| Corrupted/truncated backup, tampered backup with fixed checksum, missing sidecar, wrong key | Rejected before any data is written | Real backup + PGlite |
| Missing WAL segment | Continuity check detects it; recovery to a target beyond the gap refuses to start | Real PostgreSQL |
| Restore into empty server | Full restore + PITR, verified | Real PostgreSQL |
| Payout executed by provider, result not recorded locally | Adopted from provider; **zero** external payouts created by restore/workers | Real PostgreSQL + PGlite |
| Provider has no record of an in-flight payout | Held, funds reserved, needs attested resolution; submission afterwards looks up first and uses the same idempotency key | PGlite |
| Pending refund + unresolved reconciliation items at backup | Preserved; refund completes once | Real PostgreSQL + PGlite |

## 7. Known gaps (see the report for the full list)
No managed-service drill; no cross-region/WORM; keys in files in the drill; orphan-payout adoption is built and unit-tested but was not part of the real-PostgreSQL drill; single key for all backups; no synchronous replication; backup/restore not yet wired into scheduled CI or alerting (alert on archive failures, missing segments, backup age).
